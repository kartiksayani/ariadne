# macOS testing setup

Ariadne's production app has not been built. This guide records machine readiness
and explains the tests the scaffold must implement. Installing tools does not
complete P0.1 or prove a packaged application works.

## How the app will be tested

The normal Rust and frontend tests check validation, state changes and failure
paths, and measure executable line coverage. Every application commit requires
at least 80% weighted Rust + JS/TS coverage, including untested production files.

The native E2E test builds and opens the real macOS Tauri app. WebdriverIO types
into its WebView form and presses the button; the real frontend calls Rust, Rust
writes into a private test directory, and the test independently checks that file
and the native process identity. Later this becomes a real item/store journey
with relaunch and persistence assertions. Only the agent transport may be fake.
The [native contract](../planning/low-level/NATIVE_E2E.md) specifies the gate.

Those WebView actions are generated by JavaScript in the embedded driver.
They prove app wiring, but do not establish real OS mouse/keyboard input.
Appium's Mac2 driver uses XCTest for a separate bounded suite of native window,
keyboard and accessible menu/dialog interactions. Use the same WebDriver client
against this second server. Tray and dialog coverage depends on the application's
actual accessibility hierarchy and remains unproved until that is tested.

Native E2E results and measured coverage are separate required evidence.
Launching an instrumented app does not guarantee its Rust counters flush on exit;
any future external-process coverage capture needs a tested flush/shutdown recipe.

## Recheck the prerequisites

Run shell commands through `rtk proxy` in the owner's agent environment:

```sh
rtk proxy sw_vers
rtk proxy uname -m
rtk proxy xcode-select -p
rtk proxy xcodebuild -version
rtk proxy rustc --version
rtk proxy cargo --version
rtk proxy rustup component list --installed
rtk proxy cargo llvm-cov --version
rtk proxy node --version
rtk proxy npm --version
rtk proxy python3 --version
rtk proxy .venv-quality/bin/python --version
```

On another Mac with Rust already installed, install the quality components and
the pinned coverage command before building the scaffold:

```sh
rtk proxy rustup component add rustfmt clippy llvm-tools-preview --toolchain stable
rtk proxy cargo install cargo-llvm-cov --version 0.9.1 --locked
```

Use the full Xcode developer directory for Mac2. If it is not selected, have the
owner choose it in Xcode's Settings → Locations → Command Line Tools, then check
`xcode-select -p` again. Installation does not grant Accessibility or XCTest
automation permission. Follow a concrete test prompt and let the user grant the
required permission manually; report denied/missing permission as a blocker.
Do not run TCC bypasses or change macOS security settings automatically.

Appium 3.8.0 and `appium-mac2-driver@4.3.6` are installed in the dedicated npm
tooling project `/Users/kartik.sayani/Library/Caches/ariadne-devtools/macos-ui`.
Its safe entry point is `appium-local`, which selects the installed Node, enters
the tooling project and unsets `APPIUM_HOME` so Appium discovers its driver
dependency. This installation does not use global Appium state. On another
machine choose either that npm-project pattern or an explicit
`APPIUM_HOME` consistently for extension install, doctor and server.
[Appium extension management](https://appium.io/docs/en/latest/guides/managing-exts/)
explains the separate driver installation and `APPIUM_HOME` behavior.

The local `INSTALLATION.md` records the exact reinstall command, driver/server
commands and WDA argument arrays in `logs/wda-build-command.json` and
`logs/wda-test-command.json`. From that directory:

```sh
rtk proxy ./appium-local driver doctor mac2
rtk proxy ./appium-local --address 127.0.0.1 --port 4723 --use-drivers mac2 --log-no-colors
```

The initial real XCTest build exposed a missing `DVTDownloads.framework`, despite
doctor success. Xcode first-launch installation waited for administrator approval;
after the owner accepted the prompt it exited successfully and the framework was
present. The subsequent WDA `build-for-testing` succeeded, its loopback runner
became ready, and the real OS input probe passed. The earlier diagnosis and final
build/probe logs are retained under the tooling project's `logs/` directory.

Start the Appium server with `--address 127.0.0.1 --port 4723`. Run one test worker
in the logged-in GUI session, use bounded readiness/command deadlines, and stop
only the server/app processes created by that run. Own WebDriverAgentMac startup
and connect with `webDriverAgentMacUrl` from a fresh Appium process. In
[Mac2 4.3.6](https://github.com/appium/appium-mac2-driver/blob/v4.3.6/lib/wda-mac.ts),
process cleanup kills only tracked PIDs. Default startup separately sends
`DELETE /` to an occupied configured WDA host/port, assuming an obsolete agent
without proving ownership; the external URL avoids that occupied-port takeover.
Fail if a required port is occupied by an unrelated listener. Do not enable
relaxed security, insecure AppleScript, Full Disk Access or recording by default.
Use private disposable app data so tests never touch the owner's project history
or settings.

Build the driver's `WebDriverAgentMac.xcodeproj` with scheme
`WebDriverAgentRunner`, `build-for-testing`, `-destination platform=macOS` and a
private `-derivedDataPath`. After a successful build, use
`test-without-building` with the same project/scheme/destination/data directory and
`-parallel-testing-enabled NO`. Set `USE_HOST=127.0.0.1` and `USE_PORT=10100`
only in the spawned WDA process environment. Track that process group and bound
readiness/cleanup. A fresh Appium session must specify
`appium:webDriverAgentMacUrl=http://127.0.0.1:10100` plus the disposable app's
explicit bundle ID, app path and private environment. See the
[Mac2 capability reference](https://appium.github.io/appium-mac2-driver/latest/reference/capabilities/)
for external WDA and application options. Never use Finder or the owner's app as
the fixture, and never omit the external WDA option to fall back to the default
occupied-port takeover.

## What remains at scaffold time

The [dependency table and recipe](../planning/low-level/NATIVE_E2E.md) pin Tauri,
both WDIO plugins and the WebDriver runner. Install these as project dependencies
when the desktop scaffold exists, commit Cargo/npm lockfiles, and keep the driver
plugins out of normal and packaged builds. Current planning dependencies do not
include a production desktop application or its native test runner.
Use top-level Tauri API 2.12.1 alongside Rust/CLI 2.12.1; the old API 2.11.1 pin
failed the CLI's version check in a real locked probe. Preserve WDIO's nested
API dependency and verify the lockfile graph, following
[ADR-0003](../adr/ADR-0003-align-tauri-build-dependencies.md).

The first application commit must activate all existing application gates, run
the real native receipt test and meet measured coverage. The Mac2 supplement
adds feature-specific OS tests as those surfaces exist. Neither a driver doctor
check nor a disposable probe proves notification routing, tray behavior, install,
release packaging or other [release acceptance](../planning/low-level/VERIFICATION.md).

See [ADR-0002](../adr/ADR-0002-test-webview-and-macos-surfaces.md) for this decision.
Organization security guidance was not fetched under the owner's explicit MCP
waiver; no Seezo approval or organization-compliance claim is made.
